# Безопасность учебного проекта

## Область действия

Первая версия предназначена для локального изучения Event Sourcing. Пользователи, роли, IAM, JWT, HTTP Basic и проверка владельца кошелька пока не реализуются. Это граница задачи, а не утверждение, что открытый API подходит для публичной эксплуатации.

Не подключать Spring Security и внешние системы авторизации автоматически из-за наличия этого документа. Если в существующем проекте уже есть защита, не удалять её ради рефакторинга стиля; отметить отличие от учебного объёма.

## Конфигурация

Реальные пароли, токены и ключи передавать через переменные окружения; не коммитить .env с секретами. `.env.example` содержит только демонстрационные значения. Допускаются явно обозначенные локальные учебные DB credentials; не представлять их как production-конфигурацию.

Для локального Compose публиковать PostgreSQL на loopback. Локальный профиль приложения также должен быть предназначен для доступа с машины разработчика. Не добавлять автоматическое публичное развёртывание.

## Входные данные и SQL

- Все SQL-запросы параметризованы; пользовательские значения не интерполируются в SQL.
- Проверять UUID, размер/формат заголовков, положительные целые суммы, expectedVersion и лимиты пагинации.
- Проверять переполнение long; использовать однозначные единицы измерения — копейки.
- Не разрешать произвольные имена типов и Java-классов при десериализации событий. Реестр event_type/schema_version закрытый и явный.
- Не вводить API для произвольного редактирования/удаления сохранённых событий.

Idempotency-Key и expectedVersion защищают выполнение операций от повторов/гонок, но не являются аутентификацией или проверкой прав.

## Ошибки и логи

Не отдавать клиенту stack trace, SQL, параметры подключения и внутренние сообщения драйвера. Не логировать секреты и полные запросы. Правила logging.md обязательны и для ошибок сериализации/БД.

## Целостность истории

Обычный код приложения выполняет только INSERT/SELECT для wallet_events. Исправление бизнес-состояния осуществляется новой разрешённой операцией и событием, а не UPDATE истории. Разделение ролей БД и инфраструктурные права можно добавить отдельным этапом; пока не утверждать, что неизменность защищена от любого администратора БД.

Рефакторинг не должен пересоздавать базу, удалять Docker volume, менять сохранённые payload или запускать разрушительный rollback миграций.

## Следующий этап при необходимости

Перед появлением реальных пользователей потребуется отдельное решение по аутентификации, авторизации, владельцу кошелька и области уникальности ключей команд. Не выдумывать ownerId и не расширять модель событий сейчас ради гипотетических требований.
