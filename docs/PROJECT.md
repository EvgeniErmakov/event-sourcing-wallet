# Требования к Event Sourcing Wallet

Статус: действующая спецификация ветки `02-cqrs-sync`. Текущий этап — Event Sourcing + CQRS с синхронной моделью чтения; без Axon и асинхронных обработчиков. Автоматические тесты не входят в работу и не запускаются. Правила нового оформления не разрешают менять сохранённые события, HTTP-контракт и применённые миграции.

## 1. Учебная цель

Показать весь путь: HTTP-запрос → команда → загрузка событий → восстановление Wallet → проверка правил → новые события → атомарная запись событий, проекции и receipt → HTTP-ответ. Обычный GET читает проекцию.

Разработчик должен увидеть собственную реализацию event store, optimistic locking и идемпотентности. Необходимо объяснить, почему обычная таблица балансов с дополнительным журналом операций не удовлетворяет этому заданию.

## 2. Технологии

## 3. Предметная область

Кошелёк содержит `walletId: UUID`, `balanceMinor: long`, `currency: RUB`, `status: ACTIVE | CLOSED`, `version: long`. Объект до первого события ещё не создан; это отдельное внутреннее состояние, недоступное как существующий кошелёк через API.

Деньги — целое число копеек. Например, `100000` = 1 000 ₽. Не использовать double/float. Суммы положительные; переполнение long запрещено и обрабатывается явно, например через Math.addExact.

| Команда | Проверки | Новое событие |
|---|---|---|
| CreateWallet | Кошелёк с таким UUID отсутствует; валюта RUB | WalletCreated |
| DepositMoney | Существует, ACTIVE; amountMinor > 0; сумма не переполняется | MoneyDeposited |
| WithdrawMoney | Существует, ACTIVE; amountMinor > 0; хватает денег | MoneyWithdrawn |
| CloseWallet | Существует, ACTIVE; баланс равен 0 | WalletClosed |

Каждая успешная команда этой версии создаёт ровно одно событие. Отклонённая команда событий не создаёт. Повтор закрытия с новым ключом — ошибка состояния; повтор первоначальной команды с тем же ключом — прежний успешный результат.

Событие содержит бизнес-факт, а не просьбу выполнить действие. Payload: WalletCreated содержит currency; MoneyDeposited/MoneyWithdrawn — amountMinor; WalletClosed — пустой объект. UUID кошелька, версия и время находятся в envelope.

## 4. Организация кода

Один модуль. Сохранить существующий базовый пакет; для нового проекта — `com.example.wallet`. Контроллеры находятся в `controller`, исключения в `exception` и подпакетах, интерфейсы прикладных сервисов в `service`, реализации в `service.impl`. Остальная структура и зависимости определены в [architecture.md](architecture.md).

| Компонент | Ответственность |
|---|---|
| Wallet | Проверить команду и вернуть события; применить факт; восстановить состояние |
| WalletCommand / WalletEvent | Явные типы команд и неизменяемых событий |
| WalletCommandService / WalletCommandServiceImpl | Команды, replay, идемпотентность и общая транзакция |
| WalletQueryService / WalletQueryServiceImpl | Проекция текущего состояния, исторический replay, история и сравнение |
| WalletReadModelProjector | Синхронное применение принятых фактов в производной таблице |
| EventStore | Загрузить поток и атомарно добавить события при ожидаемой версии |
| JdbcEventStore | SQL, сравнение версий, запись и чтение JSONB |
| CommandReceiptRepository | Найти результат через find и вставить через insert; перезапись запрещена |
| EventSerializer | Стабильное имя типа + schemaVersion ↔ конкретный Java record |
| WalletController | HTTP, DTO и вызов сценариев |
| ApiExceptionHandler | Единый формат ошибок ProblemDetail |

Каждый прикладной сервис имеет интерфейс и реализацию. Контроллер внедряет интерфейс; @Service ставится на реализацию. Названия вспомогательных классов можно уточнить. Не создавать обобщённую платформу обработки сообщений.

`decide` не изменяет баланс напрямую. Полученные новые события применяются через тот же `apply`, который используется при восстановлении. `apply` не вызывает `decide` и не проверяет заново правила приёма исторической команды; допустимы проверки целостности потока и корректности сохранённых данных. Состояние объекта, полученное внутри неудачной транзакции, отбрасывается.

Время событий и UUID генерируются вне replay. Для текущего времени внедрить Clock. Повторный replay одних и тех же событий должен давать то же состояние и версию.

## 5. Хранение

В дополнение к служебным таблицам Liquibase используются четыре таблицы.

### event_streams

| Столбец | Тип | Смысл |
|---|---|---|
| stream_id | UUID PK | UUID кошелька |
| current_version | BIGINT NOT NULL, >= 0 | Техническая версия потока для контроля записи |

Это технические метаданные. Баланс и статус здесь не хранятся. Обновление current_version разрешено; бизнес-история находится в wallet_events.

### wallet_events

| Столбец | Тип | Смысл |
|---|---|---|
| event_id | UUID PK | Идентификатор факта |
| stream_id | UUID NOT NULL FK | Ссылка на event_streams |
| stream_version | BIGINT NOT NULL, > 0 | Порядок события внутри кошелька |
| event_type | VARCHAR NOT NULL | Стабильное имя: WalletCreated и т. д. |
| schema_version | INTEGER NOT NULL, > 0 | Версия JSON-формата, сейчас 1 |
| payload | JSONB NOT NULL | Данные события |
| occurred_at | TIMESTAMPTZ NOT NULL | Время события, не критерий сортировки |
| command_id | UUID NOT NULL | Ключ команды, породившей событие |

Обязательный UNIQUE(stream_id, stream_version) одновременно поддерживает упорядоченное чтение по кошельку. Приложение только вставляет и читает события. Не вводить произвольный глобальный порядковый номер и инфраструктуру подписки на события.

### command_receipts

| Столбец | Тип | Смысл |
|---|---|---|
| command_id | UUID PK | Глобальный ключ идемпотентности |
| request_fingerprint | TEXT NOT NULL | SHA-256 канонического содержания команды |
| response_status | INTEGER NOT NULL | Исходный HTTP-статус успеха |
| response_body | JSONB NOT NULL | Исходный ответ об успешной операции |
| completed_at | TIMESTAMPTZ NOT NULL | Время выполнения |

Fingerprint включает тип команды, walletId и все нормализованные поля запроса, включая expectedVersion. Пробелы и порядок полей входного JSON не влияют на него. Хранить только завершённые успешные команды; ошибки не кэшировать. Ответ в receipt — запись результата запроса, не источник состояния Wallet и не таблица балансов. Обычный GET читает wallet_read_model; исторический GET и сравнение читают события.

## 6. Атомарность и конкуренция

Использовать READ COMMITTED и явную границу транзакции в реализации прикладного сервиса (`service.impl`). Реализация может использовать TransactionTemplate, чтобы rollback и обработка конфликта были хорошо видны.

Порядок выполнения:

1. Провалидировать HTTP-запрос и вычислить fingerprint.
2. Найти receipt по commandId. При совпадении fingerprint вернуть сохранённый статус и тело без новой обработки. При несовпадении — 409 IDEMPOTENCY_KEY_REUSED.
3. В транзакции прочитать поток одним упорядоченным SELECT и восстановить Wallet. Версию брать из прочитанных событий, чтобы не сочетать разные снимки данных отдельными SELECT.
4. Проверить expectedVersion клиента и бизнес-правила, сформировать событие.
5. Для существующего потока атомарно выполнить сравнение и изменение версии: `UPDATE event_streams SET current_version = current_version + 1 WHERE stream_id = :id AND current_version = :expectedVersion`. Ноль изменённых строк означает конфликт.
6. Для создания вставить новый поток с версией 0 и выполнить append первого события по ожидаемой версии 0 в той же транзакции. Гонку создания разрешает PK stream_id.
7. Вставить событие с версией expectedVersion + 1, применить проектор и вставить результат команды в command_receipts. Все изменения фиксируются вместе.
8. Возвращать успешный HTTP-ответ только после commit.

Если происходит конфликт версии или релевантного UNIQUE/PK, сначала откатить транзакцию, затем отдельным чтением найти receipt: конкурент мог уже выполнить ту же команду. При совпадении fingerprint вернуть его ответ; при несовпадении — 409; если receipt отсутствует — вернуть исходный конфликт. Такой же повторный поиск нужен перед возвратом отказа по версии/состоянию, если параллельный дубль уже успел завершиться. Не превращать любую ошибку SQL в 409.

Не делать автоматический повтор списания с обновлённой версией. Клиент получает конфликт и может перечитать кошелёк. `expectedVersion` в HTTP не заменяет атомарный контроль в БД.

Пример: два запроса увидели баланс 100000 и версию 2, оба хотят списать 70000. Только один append по версии 2 проходит. Второй получает конфликт; баланс после первого равен 30000. Для продолжения нужна новая команда на актуальном состоянии.

## 7. REST API

Префикс `/api/wallets`. Для всех изменяющих запросов обязателен заголовок `Idempotency-Key` с UUID. Один ключ — одна неизменная команда.

| Метод и путь | Тело | Успешный ответ |
|---|---|---|
| PUT /api/wallets/{walletId} | `{ "currency": "RUB" }` | 201, созданный кошелёк, version=1 |
| POST /api/wallets/{walletId}/deposits | `{ "amountMinor": 100000, "expectedVersion": 1 }` | 200, состояние после события |
| POST /api/wallets/{walletId}/withdrawals | `{ "amountMinor": 20000, "expectedVersion": 2 }` | 200, состояние после события |
| POST /api/wallets/{walletId}/close | `{ "expectedVersion": 3 }` | 200, состояние после закрытия, если баланс 0 |
| GET /api/wallets/{walletId} | — | 200, состояние из wallet_read_model |
| GET /api/wallets/{walletId}?atVersion=2 | — | 200, состояние после события №2 |
| GET /api/wallets/{walletId}/events?afterVersion=0&limit=100 | — | 200, страница событий |
| GET /api/wallets/{walletId}/comparison | — | 200, eventState/readModel/matches из одного снимка |

Пример состояния:

```json
{
  "walletId": "11111111-1111-4111-8111-111111111111",
  "balanceMinor": 80000,
  "currency": "RUB",
  "status": "ACTIVE",
  "version": 3
}
```

Текущий GET читает проекцию, version берётся из last_event_version. Исторический GET читает события основной БД. Исторический запрос принимает только версию от 1 до последней доступной; 0/отрицательная — 400, версия выше текущей — 404 VERSION_NOT_FOUND. Отсутствующий кошелёк — 404. Отсутствие проекции существующего потока — 500 PROJECTION_INTEGRITY_ERROR без replay/backfill. Неизвестный поток — 404.

История событий: limit по умолчанию 100, диапазон 1–500; afterVersion >= 0. Возвращать `{items, nextAfterVersion, hasMore}`; читать limit+1 строк; nextAfterVersion равен версии последнего возвращённого события или исходному afterVersion при пустой странице. Сортировка stream_version ASC. Для отсутствующего кошелька — 404, для существующего без более новых событий — пустая страница. Лимит страниц истории не ограничивает полный replay Wallet.

Ошибки — application/problem+json с обычными полями ProblemDetail и расширением `code`:

- 400: некорректный JSON, UUID, заголовок, валюта, неположительная сумма, дробное значение для целочисленного поля, некорректная версия/параметр. Не округлять дробные суммы молча.
- 404: WALLET_NOT_FOUND, VERSION_NOT_FOUND.
- 409: WALLET_ALREADY_EXISTS, VERSION_CONFLICT, IDEMPOTENCY_KEY_REUSED, WALLET_CLOSED, INSUFFICIENT_FUNDS, NON_ZERO_BALANCE, BALANCE_OVERFLOW.
- 500: повреждённая история, неизвестный тип/schemaVersion, отсутствующая/повреждённая проекция (PROJECTION_INTEGRITY_ERROR), неожиданная ошибка сервера. Не раскрывать SQL/stack trace клиенту; подробности оставить в логе.

Повтор успешной команды возвращает первоначальный ответ даже если кошелёк уже изменился другими командами. Это результат именно той операции; актуальное состояние запрашивается через GET.

## 9. Критерии завершения без тестов

- Реализованы указанные операции и API, исходники документированы.
- В коде прослеживается восстановление из событий и одна транзакция записи.
- Производная wallet_read_model обновляется в транзакции команды; snapshots и внешнего брокера нет.
- Liquibase описывает таблицы, ограничения и индексы; схема не создаётся другими механизмами.
- Сборка `bootJar` выполнена, если окружение позволяет; результат отражён честно.
- Обычный запуск приложения и выполнение миграций допускаются, но отсутствие окружения сообщается отдельно. HTTP-сценарии и тесты не запускаются.
- README соответствует фактическому коду. Сборка сама по себе не доказывает корректность гонок и идемпотентности; автоматические проверки поведения отложены пользователем.

## 10. Осознанные ограничения

Отдельный Angular UI в `frontend` разрешён текущим запросом пользователя и реализован
для ручного создания кошельков, операций, истории, исторического просмотра и демонстрации
идемпотентности и сравнения моделей. Добавлены wallet_read_model и диагностический /comparison. Правила клиента и безопасного диапазона
чисел — в [frontend.md](frontend.md); установка и запуск — в README.
Для frontend разрешены установка зависимостей и production-сборка без тестов.
Браузерные, API-, smoke- и прочие автоматические сценарии по-прежнему исключены.

Полный replay имеет стоимость O(N) по количеству событий кошелька. Это выбранная учебная реализация; snapshots будут отдельным следующим этапом при необходимости.

Модель чтения синхронная. Сейчас нет асинхронных проекций, eventual consistency, Kafka, Axon, outbox, межкошельковых переводов, авторизации, метрик и upcasters. SchemaVersion=1 и явный реестр подготовлены для дальнейшего обсуждения эволюции событий. Не реализовывать перечисленное заранее.

## 12. Реализация шага 2

Контроллер внедряет WalletCommandService и WalletQueryService. Реализации находятся в service.impl.
WalletCommandServiceImpl сохраняет прежний внешний READ COMMITTED/REQUIRES_NEW; проектор
вызывается после append и до receipts.insert без новой транзакции. Ошибка проекции откатывает
версию, событие и receipt вместе с производными изменениями. Повтор готового receipt не вызывает проектор.
Fingerprint, сохранённые event_type/schema_version/payload и тела ответов команд сохранены.

### wallet_read_model

wallet_id UUID PK/FK, balance_minor BIGINT >= 0, currency RUB, status ACTIVE/CLOSED,
last_event_version BIGINT > 0, все поля NOT NULL; CLOSED означает нулевой остаток.
Проектор применяет версии последовательно: создание только на версии 1, UPDATE только при v-1.
Пропуск, повтор, отсутствие строки, недопустимое состояние и переполнение дают ошибку целостности.
WalletReadModel — отдельный тип, не сущность Wallet и не источник бизнес-решений.

### Сравнение и запуск на чистой БД

Сравнение возвращает eventState, readModel и matches. WalletState.equals сравнивает все поля;
отсутствующая строка представлена null на HTTP-границе и всегда даёт matches=false.
Оба чтения выполняются внутри одной read-only REPEATABLE READ транзакции непосредственно
через репозитории. Обычный GET сравнение не запускает. UI вызывает его только по кнопке.
