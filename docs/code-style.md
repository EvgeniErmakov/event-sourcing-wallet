# Стиль Java-кода

## Общие требования

Кодировка UTF-8, четыре пробела без табуляции, длина строки до 140 символов. Один top-level тип на файл. Имена Java/API/SQL — на английском; JavaDoc, объясняющие комментарии и документация — на русском.

| Элемент | Стиль |
|---|---|
| Класс, интерфейс, record, enum | UpperCamelCase |
| Метод, переменная, поле | lowerCamelCase |
| Константа, enum-значение | UPPER_SNAKE_CASE |
| Пакет | lowercase |
| HTTP DTO | CreateWalletRequestDto, WalletResponseDto |
| Контроллер | WalletController, в controller |
| Прикладной сервис | WalletCommandService, в service |
| Реализация сервиса | WalletCommandServiceImpl, в service.impl |
| Репозиторий | CommandReceiptRepository, реализация JdbcCommandReceiptRepository |
| Хранилище событий | EventStore, реализация JdbcEventStore |
| Исключение | Содержательное имя с Exception, в exception и его подпакетах |

В собственных именах писать Id, Dto, Json, Http вместо ID, DTO, JSON, HTTP. Правило не относится к именам стандартных типов UUID/URI, внешним API и константам.

## Интерфейсы и типы

Прикладные сервисы обязательно разделены на интерфейс и реализацию. Не использовать префикс I. Не создавать интерфейсы для каждого вспомогательного класса.

DTO, команды, события и неизменяемые результаты удобно выражать record. Команды и события можно объединять sealed interface. Wallet — доменный объект с закрытым состоянием, а не DTO и не @Entity. Не добавлять публичные setters для баланса или статуса: изменения происходят через применение событий.

EventStore — разрешённое осмысленное имя, его не нужно переименовывать ради обязательного суффикса Repository. Методы append, insert, apply, decide, rehydrate соответствуют предметной области и не заменяются механически на save/update.

## Поля, конструкторы, методы

Порядок: константы, static-поля при необходимости, поля экземпляра и final-зависимости, конструкторы, публичные методы, методы package-private/protected, приватные методы, вложенные типы. Перегрузки держать рядом; при конфликте с группировкой по доступу приоритет у логической близости.

Dependency injection — явный конструктор и final-поля. Lombok не подключать. Логгер — SLF4J LoggerFactory. Константы располагать в минимальной необходимой области; общий Constants-класс без предметного смысла не создавать.

Названия коллекций — во множественном числе: events, receipts. Локальные переменные содержательные; i/j допустимы для коротких счётчиков. Boolean-методы используют is/has/can/should/exists; accessor record и внешние переопределяемые методы — исключение.

## Отсутствие результата

Для необязательного одиночного результата возвращать Optional, для коллекции — пустую коллекцию. Не преобразовывать Optional в null в промежуточных методах:

```java
private Optional<CommandReceipt> findReceipt(UUID commandId) {
    return inRead(() -> receipts.find(commandId));
}
```

После такого изменения обновить вызывающий код; сохранить семантику rollback и повторного чтения. Не использовать Optional как поле DTO или параметр каждой операции. Отсутствие обязательного кошелька — доменная/прикладная ошибка, а отсутствие receipt — обычное состояние.

## Размер методов

20–30 строк метода, до 20 строк лямбды и до 4 параметров — ориентиры читаемости, а не основания дробить атомарную операцию на разные транзакции. Вспомогательный метод, вызванный внутри TransactionTemplate, остаётся частью той же операции.

Не объединять несвязанные параметры в искусственный DTO только для соблюдения лимита. Длинный switch по явно перечисленным событиям или record с несколькими полями допускается при читаемом оформлении.

## Исключения

Не проглатывать ошибки записи, конфликты или неизвестные события. Пустой catch с комментарием сам по себе не является корректной обработкой. Ловить ожидаемые конкретные исключения; общий обработчик неожиданных ошибок допустим в exception.api.

Не превращать любую DataAccessException в конфликт версии: распознавать конкретную причину/ограничение. Причину исключения сохранять; SQL и stack trace клиенту не отдавать.

## JavaDoc и комментарии

Документировать каждый значимый тип и метод: ответственность, входные условия, результат, ошибки и побочные эффекты. Особое внимание decide/apply/rehydrate, append, идемпотентности и границам транзакции. @Override не освобождает от пояснения нетривиальной реализации; общий контракт можно описать на интерфейсе и сослаться через inheritDoc.

Комментарии объясняют причины, а не очевидные присваивания. Документация события описывает его исторический смысл, единицы измерения и payload. Не менять сохранённые event_type под новое Java-имя ради стиля.

## Типы CQRS

WalletCommandService/WalletCommandServiceImpl и WalletQueryService/WalletQueryServiceImpl
разделяют сценарии записи и чтения.
WalletReadModelProjector — небольшой компонент применения фактов, без искусственной пары Impl.
WalletReadModel — отдельный record; Wallet остаётся чистым доменным объектом.
WalletComparison хранит Optional отсутствующей проекции; только HTTP DTO отображает её как null.
JavaDoc проектора объясняет проверку версии, общую транзакцию и отличие факта от команды.
