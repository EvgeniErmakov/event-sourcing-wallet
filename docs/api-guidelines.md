# REST API кошельков

## Границы API

Все REST-контроллеры располагаются только в пакете `controller`, глобальный обработчик исключений — в `exception.api`. Контроллер зависит от интерфейса WalletService, не от WalletServiceImpl и не от JDBC-репозитория.

Контроллер принимает DTO, валидирует формат, преобразует запрос в команду и возвращает результат. Бизнес-правила проверяет Wallet; транзакцией управляет реализация сервиса. SQL, replay и обработку гонок в контроллер не переносить.

## Контракт

При рефакторинге сохранять существующие пути, JSON-поля, HTTP-статусы и Idempotency-Key. Суффикс Dto меняет имя Java-типа, но не JSON-контракт. Не вводить /api/v1, не переименовывать /close и не менять PUT на POST ради единого стиля.

Целевой контракт проекта:

| Метод и путь | Назначение |
|---|---|
| PUT /api/wallets/{walletId} | Создать кошелёк с заданным клиентом UUID |
| POST /api/wallets/{walletId}/deposits | Пополнение |
| POST /api/wallets/{walletId}/withdrawals | Списание |
| POST /api/wallets/{walletId}/close | Закрытие при нулевом балансе |
| GET /api/wallets/{walletId} | Текущее состояние, восстановленное из событий |
| GET /api/wallets/{walletId}?atVersion=N | Состояние после события N |
| GET /api/wallets/{walletId}/events?afterVersion=0&limit=100 | Страница истории |

PUT здесь создаёт ресурс по известному URI; существующий кошелёк не перезаписывается. Повтор той же команды определяется Idempotency-Key. Закрытие добавляет WalletClosed, а не удаляет историю.

## DTO и валидация

Входные DTO — в dto.request, выходные — в dto.response; использовать неизменяемые records. Команды и события не переименовывать в DTO: у них другая ответственность.

Проверять UUID, обязательные поля, RUB, положительное целое amountMinor, целую expectedVersion и диапазоны параметров. Не округлять дробную сумму до целого. Денежные значения — копейки; примеры и JavaDoc должны явно указывать единицы.

Для изменяющих операций обязателен UUID-заголовок Idempotency-Key. Для существующего кошелька expectedVersion передаётся в запросе. Повтор успешной команды возвращает первоначальные статус и тело; для актуального состояния после других операций используется GET.

## Статусы и ошибки

| Статус | Смысл |
|---|---|
| 200 | Успешное чтение, пополнение, списание или закрытие |
| 201 | Кошелёк создан |
| 400 | Ошибка формы/типа/диапазона входных данных |
| 404 | Кошелёк или запрошенная версия отсутствует |
| 409 | Конфликт версии, ключа, существования или бизнес-состояния |
| 500 | Повреждённая история, неизвестный формат события, неожиданная ошибка |

Глобальный @RestControllerAdvice возвращает application/problem+json с ProblemDetail и устойчивым полем code. Сохранить коды из PROJECT.md и текущей реализации. Не вводить параллельный ErrorResponseDto. Не отдавать SQL, пароли, stack trace и детали JDBC.

В контроллерах не ловить бизнес-ошибки через try/catch. @ExceptionHandler и собственные исключения находятся в exception и его подпакетах.

## Пагинация и чтение

История ограничена limit: default 100, диапазон 1–500. Пагинация по stream_version; afterVersion >= 0. Возвращать items, nextAfterVersion и hasMore. Параметр atVersion ограничен существующими положительными версиями.

Пагинация HTTP-истории не должна обрезать replay: для восстановления текущего Wallet нужны все его события. GET читает основную БД; отдельной проекции и асинхронной query-модели нет.
