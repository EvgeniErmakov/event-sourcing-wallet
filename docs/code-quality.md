# Качество реализации

## Решение пользователя о проверках

На текущем этапе не создавать и не запускать unit-, integration-, e2e-, smoke- и нагрузочные тесты. Не добавлять JUnit, Mockito, Testcontainers, test starters, JaCoCo, fixtures, src/test и скрипты с автоматическими проверками API/БД. Существующие пользовательские тесты не удалять; не изменять и не запускать без новой задачи.

Разрешены просмотр исходников, поиск ссылок, разрешение зависимостей, компиляция и упаковка через `./gradlew bootJar -x test`. В рамках этой задачи приложение и миграции не запускаются; ручные сценарии приведены для пользователя. Не запускать Gradle test/check/build. Если bootJar в данном проекте зависит от тестов, не выполнять их автоматически: указать ограничение.

Для Angular UI разрешены установка зависимостей и production-сборка `npm run build`.
Unit/integration/e2e/smoke, браузерные сценарии, spec-файлы и тестовые зависимости запрещены.
Сборка проверяет компиляцию TypeScript и шаблонов, но не доказывает поведение интерфейса.

Отсутствие тестов — ограничение этапа, а не рекомендация для эксплуатации. Не утверждать, что компиляция доказывает правильность конкурентных операций. Не вводить требования CI, pull request и обязательного approve другого разработчика, если пользователь не просил этот процесс.

## Что проверять чтением кода

- События остаются источником истины; команды выполняют replay, текущий GET читает производную проекцию.
- Wallet содержит инварианты, сервис управляет сценарием, JDBC-репозиторий выполняет SQL.
- Replay детерминирован, не создаёт событий и внешних эффектов.
- Append защищён ожидаемой версией в БД.
- События Axon, aggregate sequence и receipt принадлежат транзакции команды; проекция и её позиция — одной отдельной транзакции обработчика.
- Дубликат команды не перезаписывает receipt; конфликты после rollback обрабатываются вне завершённой транзакции.
- Неизвестные event_type/schema_version и разрыв версий не пропускаются молча.
- Изменения Java-пакетов не меняют event_type, JSON payload, историю или API.
- Контроллеры в controller, исключения в exception, интерфейсы сервисов в service, реализации в service.impl.
- Все изменения схемы проводятся Liquibase; начальные changesets этапа 04 после формирования неизменяемы.

## Поддерживаемость

Изменения должны решать текущую задачу. Не создавать универсальный Event Sourcing framework, command bus, абстрактные базовые сервисы и несколько новых модулей ради нескольких операций.

Декомпозировать по ответственности, но сохранять понятность транзакции. Интерфейсы прикладных сервисов обязательны по принятому стилю. Дополнительные технические интерфейсы нужны только при реальной границе или существующем контракте.

## Документация

Поддерживать JavaDoc, docs/PROJECT.md и README согласованными с кодом. Объяснять почему используется append, expectedVersion, replay, fingerprint и повторное чтение после rollback. Примеры curl/SQL — документация для пользователя, а не автоматически запускаемые сценарии.

## Отчёт о завершении

Указать изменённые части, ключевые пути, команду запуска, фактически выполненную сборку и ограничения окружения. Отдельно написать: тесты по запросу пользователя не создавались и не запускались. Если найден риск без проверки поведения, назвать его, не заявляя гарантию production readiness.

## Проверка CQRS чтением кода

- Receipt-повтор не запускает проектор; команды не читают проекцию для бизнес-решений.
- Проектор использует предыдущую версию и не выполняет upsert или собственный commit.
- GET не восстанавливает отсутствующую строку; /comparison сверяет проекцию с историей на общей бизнес-версии.
- На чистой БД Liquibase создаёт таблицы событий Axon, JDBC tokens, receipts и read model до первого запроса.
- Схема не создаётся Java-кодом; read model наполняется только streaming processor Axon из принятых событий.
- Frontend проверяет весь JSON сравнения через parseSafeJson и отбрасывает устаревшие ответы.
