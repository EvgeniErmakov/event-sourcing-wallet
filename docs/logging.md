# Логирование Event Sourcing Wallet

## Инструменты

SLF4J + Logback, предоставляемые используемой конфигурацией Spring Boot. Логгер объявлять явно через LoggerFactory; Lombok не подключать. Не добавлять Spring AI, OpenTelemetry, Zipkin, Langfuse или внешние сервисы наблюдаемости в рамках текущего этапа.

## Уровни

Логи выводятся в консоль, уровень приложения по умолчанию — INFO. Для подробной локальной
диагностики задайте `WALLET_LOG_LEVEL=DEBUG`. Используются обычные вызовы SLF4J в сервисе,
репозитории и обработчике ошибок; собственного HTTP-фильтра логирования нет.

| Уровень | Назначение |
|---|---|
| ERROR | Неожиданная ошибка, повреждённый поток, неподдерживаемый формат события, ошибка доступа к хранилищу |
| WARN | Ситуация, требующая внимания: необычная частота конфликтов или повторяющаяся эксплуатационная проблема |
| INFO | Завершённые бизнес-операции и жизненный цикл приложения |
| DEBUG | Технические детали локальной диагностики: загрузка потока, версия, число событий |

Обычное отклонение списания и единичный ожидаемый конфликт версии не обязаны быть ERROR/WARN. Не записывать stack trace для каждого нормального бизнес-отказа.

## Что логировать

Для диагностики подходят commandId, walletId, eventId, eventType, expectedVersion, resultingVersion, количество загруженных событий и стабильный код ошибки. Использовать параметризованные сообщения: `log.info("Command completed: commandId={}, walletId={}, version={}", ...)`.

Payload, responseBody и полный объект команды автоматически не логировать. Не логировать DB password, JDBC URL с credentials, токены, заголовки авторизации и весь HTTP-запрос. Суммы и содержимое кошелька выводить только при конкретной необходимости локальной диагностики.

## Транзакции и replay

Сообщение об успешной бизнес-операции писать только после commit, в этой ветке — после успешного возврата CommandGateway. Строка «списание выполнено» перед commit может остаться в логе после rollback и ввести в заблуждение.

При повторе Idempotency-Key не логировать повтор как новое списание; допустимо DEBUG о возврате сохранённого результата.

Replay не создаёт бизнес-логи вида «деньги списаны». Сводную техническую запись о восстановлении можно делать в сервисе/репозитории, вне доменного apply. Domain не зависит от логирования для своего поведения.

## Ошибки

Не логировать одну ошибку со stack trace во всех слоях. Обычно достаточно глобального обработчика или места, где ошибка окончательно обработана. Если исключение оборачивается, сохранять cause. В HTTP-ответе использовать безопасное сообщение и код, подробности оставлять в журнале.

Логи не являются event store, а запись события в PostgreSQL не заменяется логированием.

## Проекция

Ошибки обработки порции журналирует streaming processor Axon; они не проглатываются.
Один segment означает возможную остановку продвижения всех кошельков. Успех команды можно
логировать только после возврата gateway, который ожидает commit. Не логировать payload и credentials.
