# Event Sourcing простым языком

Этот документ объясняет паттерн на примере кошелька из проекта. Отдельно разобраны
оптимистический контроль версий, блокировки PostgreSQL и повторные запросы — механизмы,
которые помогают безопасно сохранять события.

Примеры Java — фрагменты для чтения, а не отдельное приложение. Сокращения отмечены явно.
SQL приведён для объяснения; выполнять его вручную для изучения документа не требуется.

## 1. Главная идея: хранить произошедшие изменения

Представим обычную таблицу кошельков:

```text
wallet_id = A
balance = 700 рублей
```

Она показывает текущий баланс. По одной этой строке нельзя понять, как он появился.

В Event Sourcing сохраняется последовательность фактов:

| Версия | Событие | Баланс после применения |
|---|---|---|
| 1 | Кошелёк создан | 0 ₽ |
| 2 | Зачислено 1 000 ₽ | 1 000 ₽ |
| 3 | Списано 300 ₽ | 700 ₽ |

Текущее состояние получается применением событий по порядку. В нашем проекте отдельной
таблицы текущего баланса нет: источником истины служит `wallet_events`.

Это отличается от обычного журнала рядом с таблицей балансов. В таком журнале история может
быть вспомогательной, а здесь без событий нельзя восстановить кошелёк.

Сохранённые события приложение не переписывает. Ошибку бизнес-операции исправляют новой
разрешённой операцией и новым фактом. Специальной команды отмены в текущем проекте нет.

## 2. Команда и событие — разные вещи

Команда выражает намерение: «хочу списать деньги». Событие фиксирует принятое изменение:
«деньги списаны».

```java
// Клиент хочет списать 300 рублей, считая текущую версию равной 2.
var command = new WalletCommand.WithdrawMoney(30_000L, 2L);

// После успешной проверки правил можно сформировать факт списания.
var event = new WalletEvent.MoneyWithdrawn(30_000L);
```

Деньги здесь выражены в копейках: `30_000L` — 300 рублей. Используется `long`, чтобы не
получать ошибки округления дробных чисел. Переполнение при сложении проверяется явно.

Команду можно отклонить: например, денег недостаточно или кошелёк закрыт. В этом случае
новое событие не сохраняется. Само создание объекта события в памяти ещё не означает,
что операция зафиксирована: нужен успешный commit транзакции.

## 3. Что такое агрегат и поток событий

Агрегат в этом проекте — объект `Wallet`, объединяющий состояние кошелька и его правила:
нельзя списать больше остатка, пополнить закрытый кошелёк или закрыть ненулевой баланс.

Поток — история одного кошелька. У разных кошельков свои версии:

```text
Кошелёк A: 1 → 2 → 3 → 4
Кошелёк B: 1 → 2
```

Версия — порядковый номер события внутри потока. Она не является временем или общим
счётчиком всех операций системы. Сортировка при восстановлении идёт по `stream_version`.

Каждый запрос восстанавливает свой объект `Wallet` в памяти. Общего Java-объекта кошелька,
к которому обращаются все запросы, нет.

## 4. Три главных метода: decide, apply, rehydrate

### decide: проверить намерение

`decide(command)` проверяет правила и возвращает новые события. Сам баланс он не меняет.

Упрощённый фрагмент обработки списания, после общих проверок версии и статуса:

```java
case WalletCommand.WithdrawMoney c -> {
    requireAmount(c.amountMinor());
    if (balanceMinor < c.amountMinor()) {
        throw failure(INSUFFICIENT_FUNDS, "Недостаточно средств");
    }
    yield List.of(new WalletEvent.MoneyWithdrawn(c.amountMinor()));
}
```

### apply: применить факт

`apply(event)` изменяет состояние объекта по событию. Например, ветка списания в проекте:

```java
case WalletEvent.MoneyWithdrawn e -> {
    requireActiveFact();
    if (e.amountMinor() <= 0 || e.amountMinor() > balanceMinor) {
        throw corrupt("Некорректное списание");
    }
    balanceMinor -= e.amountMinor();
}
```

После обработки события метод увеличивает `version`. Состояние изменяется только через
`apply`, поэтому новые операции и восстановление истории используют одну логику изменения.

Проверки в `apply` выявляют повреждённую историю. Они не должны заново применять новые
правила приёма команд. Например, будущий лимит на новое пополнение нельзя автоматически
распространять на старые, уже принятые пополнения.

### rehydrate: восстановить состояние

Реальный метод из `Wallet`:

```java
public static Wallet rehydrate(UUID walletId, List<WalletEvent> events) {
    Wallet wallet = new Wallet(walletId);
    events.forEach(wallet::apply);
    return wallet;
}
```

Он создаёт пустой объект и применяет историю. Этот процесс называется replay.

Replay не вызывает `decide`, не записывает события повторно, не отправляет сообщения и не
генерирует новое время или UUID. Одна и та же история должна давать одно и то же состояние.
Порядок и непрерывность номеров событий проверяет хранилище до передачи фактов агрегату.

## 5. Зачем нужны три таблицы

| Таблица | На какой вопрос отвечает | Пример |
|---|---|---|
| `wallet_events` | Что произошло с кошельком? | Зачислено 10 000 копеек, версия 2 |
| `event_streams` | Какая версия потока сейчас зафиксирована? | Кошелёк A, версия 2 |
| `command_receipts` | Какой ответ уже получили для этой команды? | Ключ K, HTTP 200, тело ответа |

`wallet_events` содержит неизменяемую историю. Из неё восстанавливаются баланс и статус.

`event_streams` содержит технические метаданные для защиты записи: UUID потока и его версию.
Баланса в этой таблице нет.

`command_receipts` хранит результат успешно выполненного запроса. В нём есть ключ команды,
отпечаток её содержимого, исходный HTTP-статус и тело ответа. Это позволяет ответить на повтор,
не выполняя команду снова. Неуспешные команды в текущем проекте туда не записываются.

Хотя тело ответа в receipt содержит баланс, использовать его как текущий баланс нельзя.
После этой команды могли произойти другие события. Текущий GET читает историю событий.

Одна успешная новая команда в этом проекте создаёт одно событие и один receipt. Повтор
успешной команды использует прежний receipt и не добавляет событие. В других реализациях
Event Sourcing одна команда может создавать несколько событий.

## 6. Как проходит новая операция

```text
HTTP-запрос
  → проверка DTO и Idempotency-Key
  → вычисление fingerprint и поиск receipt
  → если найден подходящий receipt: вернуть прежний ответ
  → иначе начать транзакцию записи
      → загрузить события
      → восстановить Wallet
      → decide: проверить команду и сформировать событие
      → apply: применить событие к локальному объекту
      → append: проверить версию в БД и записать событие
      → вставить receipt
  → commit
  → вернуть успешный HTTP-ответ
```

Ответственность разделена: контроллер работает с HTTP, `Wallet` — с бизнес-правилами,
`WalletServiceImpl` организует сценарий и транзакцию, `JdbcEventStore` выполняет SQL.

## 7. Почему проверка версии в Java недостаточна

Представим: на кошельке 1 000 рублей, версия 2. Одновременно пришли два разных запроса
списать по 700 рублей.

Оба могут прочитать одну историю и восстановить баланс 1 000 рублей. У обоих проверка
`balanceMinor >= amountMinor` проходит. Каждый Java-объект пока не знает о конкуренте.

Проверка клиентской версии в `decide` выявляет уже устаревшие запросы:

```java
if (command.expectedVersion() != version) {
    throw failure(VERSION_CONFLICT, "Версия кошелька изменилась");
}
```

Но между этой проверкой и записью другой запрос может успеть изменить поток. Поэтому
окончательное сравнение и изменение версии выполняются одной операцией в базе данных.

## 8. Оптимистический контроль: сравнить и изменить

В `JdbcEventStore.append` используется такой SQL:

```sql
UPDATE event_streams
SET current_version = current_version + 1
WHERE stream_id = :id
  AND current_version = :expected;
```

Его смысл: «увеличь версию, только если она всё ещё равна той, которую я прочитал».
Это называют compare-and-set, или CAS.

Количество обновлённых строк сообщает результат:

```java
if (updated == 0) {
    throw new WalletException(VERSION_CONFLICT, "Поток изменён конкурентом");
}
```

Одна строка обновлена — можно продолжить запись. Ноль строк — ожидаемая версия не найдена,
сохранение этой операции нужно прервать.

В примере со списаниями первый запрос изменит версию с 2 на 3 и сохранит списание.
Второй уже не сможет обновить строку с условием `current_version = 2`. После commit первой
операции баланс составит 300 рублей, а второй запрос получит конфликт.

Автоматически подставлять новую версию и повторять списание здесь нельзя. Пользователь
должен получить актуальное состояние и решить, нужна ли новая команда с новым ключом.

`synchronized` эту гарантию не заменяет: он управляет доступом внутри одной JVM,
а к одной БД могут обращаться несколько экземпляров приложения.

## 9. Кто удерживает блокировку строки

Блокировку обеспечивает PostgreSQL при `UPDATE`. Вручную хранить её в Java не требуется.
При нормальном выполнении она удерживается до завершения транзакции:

```text
Начало транзакции
  UPDATE event_streams   ← строка заблокирована
  INSERT wallet_events  ← блокировка остаётся
  INSERT command_receipts
COMMIT / ROLLBACK        ← блокировка освобождается
```

Если второй запрос пытается обновить ту же строку, он ждёт завершения первого.
При используемом уровне изоляции `READ COMMITTED` после commit конкурента PostgreSQL
повторно проверяет условие UPDATE на обновлённой строке. Старая версия уже не совпадёт.

Если первая транзакция откатится, её изменение версии исчезнет. Второй запрос сможет
продолжить, если условие по версии остаётся выполненным.

Обычный SELECT без запроса блокировки может читать последнее зафиксированное состояние.
Блокировка строки не означает, что вся таблица стала недоступна для чтения.

Почему контроль называется оптимистическим, хотя блокировка есть? Мы не блокируем кошелёк
заранее на время чтения и бизнес-проверок. Проверяем, что никто не опередил нас, при записи.
Сам UPDATE всё равно использует механизм блокировок базы данных.

Дополнительная защита — уникальность пары `(stream_id, stream_version)` в `wallet_events`:
два события одного кошелька не могут занять одну версию. При создании кошелька гонку вставок
потока разрешает первичный ключ `event_streams.stream_id`.

## 10. Зачем общая транзакция

Вместе должны сохраниться три изменения: новая версия потока, событие и receipt.
Иначе возможны противоречия: например, деньги уже зачислены, а результата для повтора нет.

В сервисе используется `TransactionTemplate`. Сокращённая форма вызова:

```java
CommandReceipt completed = write.execute(ignored ->
        executeInTransaction(walletId, commandId, command, fingerprint));
// При обычном успешном возврате write.execute транзакция уже зафиксирована.
return completed;
```

`executeInTransaction` выполняет сценарий, включая `events.append(...)` и
`receipts.insert(...)`, на одной транзакции. Если запись не удалась, изменения откатываются.
Успешный HTTP-ответ возвращается только после commit.

В памяти `wallet.apply(event)` уже мог изменить объект. Rollback не отменяет Java-присваивания:
этот локальный объект просто отбрасывается. Следующий запрос снова восстановит состояние из БД.

## 11. Идемпотентность: повтор не должен менять баланс ещё раз

Сервер успешно пополнил кошелёк, но ответ потерялся в сети. Клиент не знает, что произошло,
и повторяет запрос. Без защиты это могло бы привести к повторному пополнению.

Клиент передаёт UUID в заголовке `Idempotency-Key`. Для повторения той же команды он сохраняет
прежний ключ и все параметры запроса.

Перед выполнением сервер ищет receipt:

```java
private Optional<CommandReceipt> findReceipt(UUID commandId) {
    Optional<CommandReceipt> receipt = inRead(() -> receipts.find(commandId));
    log.debug("Поиск receipt: commandId={}, found={}", commandId, receipt.isPresent());
    return receipt;
}
```

`receipts.find` читает запись по ключу. `inRead` выполняет это в отдельной транзакции чтения.
`Optional` содержит найденный результат либо пуст, если успешного результата пока нет.
Лог сообщает только факт нахождения; он ничего не сохраняет в таблицу receipts.

Отсутствие receipt ещё не доказывает, что другой запрос не выполняет ту же команду прямо
сейчас. Поэтому нужны и уникальность ключа в БД, и обработка конкурентного завершения.

## 12. Зачем fingerprint и SHA-256

`commandId` отвечает на вопрос «какую команду клиент повторяет?». `fingerprint` позволяет
проверить, что содержание действительно прежнее.

```java
String fingerprint = CommandFingerprint.of(walletId, command);
```

Для пополнения сначала формируется нормализованная строка примерно такого вида:

```text
11111111-1111-4111-8111-111111111111
DepositMoney
10000
1
```

Это UUID кошелька, тип команды, сумма в копейках и ожидаемая версия. Между полями — перевод
строки. Затем вычисляется SHA-256; его шестнадцатеричная запись имеет длину 64 символа.

Хешируется содержание команды, а не исходный JSON. Поэтому перестановка JSON-полей
или пробелы не меняют отпечаток. Для создания учитывается валюта, для закрытия — версия.

| Повторный запрос | Результат |
|---|---|
| Прежний ключ, прежние параметры | Возвращаем исходный ответ |
| Прежний ключ, другая сумма или версия | `409 IDEMPOTENCY_KEY_REUSED` |
| Новый ключ | Обрабатываем новую команду с обычными проверками |

Хеширование удобно для хранения и сравнения, но принципиально можно сравнивать сами
нормализованные поля. Это не шифрование и не электронная подпись. Совпадение хешей разных
входов теоретически возможно; SHA-256 выбран с практически пренебрежимой вероятностью коллизии.

Формат нормализации нельзя произвольно менять: старые receipts содержат отпечатки,
вычисленные по прежним правилам.

## 13. Почему после конфликта снова ищут receipt

Два одинаковых запроса могут одновременно не найти receipt и начать выполнение.
Первый сохранит результат. Второй столкнётся с конфликтом версии или уникальности ключа.

Правильный порядок обработки:

```text
Конфликт при выполнении
  → rollback транзакции записи
  → отдельная транзакция чтения receipt
      → найден, fingerprint совпал: вернуть прежний успех
      → найден, fingerprint другой: вернуть конфликт ключа
      → не найден: вернуть исходную ошибку
```

После SQL-ошибки PostgreSQL транзакция может находиться в аварийном состоянии: продолжать
чтение в ней нельзя. В проекте исключение обрабатывается снаружи `write.execute`, когда
rollback уже завершён, а `findReceipt` открывает отдельную транзакцию чтения.

Повторная проверка нужна и при отказе по версии или состоянию: одинаковая команда могла
завершиться между первоначальным поиском receipt и восстановлением кошелька.

Receipt только вставляется и читается. Перезаписывающий upsert уничтожил бы исходный
результат и нарушил смысл повторного запроса.

## 14. Как читать текущее и прошлое состояние

Для текущего состояния загружается полный поток кошелька и вызывается `rehydrate`.
Для состояния на версии 2 применяются только первые два события:

```text
Версия 1: создан             → 0 ₽
Версия 2: зачислено 1 000 ₽   → 1 000 ₽   ← результат atVersion=2
Версия 3: списано 300 ₽       → 700 ₽     ← текущее состояние
```

Пагинация списка событий на экране — отдельная операция. Если UI показывает только
20 событий, это не означает, что сервер восстанавливает текущий баланс по этим 20 событиям.

## 15. Тип события и версия JSON

Событие хранится вместе с техническими полями: UUID, номером в потоке, временем и ключом
команды. Его полезная нагрузка, или payload, содержит бизнес-данные:

```json
{
  "amountMinor": 10000
}
```

`event_type = MoneyDeposited` говорит, какой это факт. `schema_version = 1` задаёт версию
формата payload. Это другая версия, не `stream_version`, определяющая порядок в истории.

Реестр в `EventSerializer` связывает сохранённый тип с Java-событием. Перенос Java-класса
в другой пакет не должен менять сохранённое имя события. Неизвестный тип или формат нельзя
молча пропускать: иначе восстановленный баланс может оказаться неверным.

## 16. Нужны ли Spring Data, Kafka и CQRS

Event Sourcing задаёт способ хранения и восстановления состояния, а не обязательный набор
библиотек. В этом проекте достаточно PostgreSQL, Spring JDBC и транзакций Spring.

Spring Data сама по себе не реализует описанную обработку команд. Здесь SQL оставлен явным,
чтобы были видны сравнение версии, вставка события и сохранение receipt. Spring JDBC уже
участвует в транзакциях Spring; для этого не требуется Spring Data или Hibernate.

Kafka и отдельная модель чтения тоже не обязательны. Текущий сервис синхронно записывает
события в PostgreSQL и читает их оттуда. Он не использует брокер, snapshots или проекции.
Receipt и отдельная таблица метаданных — решения этой реализации, а не обязательные таблицы
любого приложения с Event Sourcing.

## 17. Что даёт паттерн и чем за это платим

Преимущества — объяснимая история изменений, возможность восстановить прошлое состояние
и проследить, какие факты привели к текущему балансу.

Цена — необходимость поддерживать форматы старых событий, аккуратно обрабатывать повторы
и конкуренцию, а также читать историю для восстановления. В этой реализации полный replay
имеет стоимость O(N), где N — количество событий кошелька.

Для простого CRUD без потребности в истории такой подход может быть избыточным. Здесь он
выбран, чтобы изучить обработку команд и хранение бизнес-фактов на небольшом примере.
