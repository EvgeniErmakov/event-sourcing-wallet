# PostgreSQL и Liquibase

## Единственный механизм миграций

Все изменения схемы выполняются строго через Liquibase. Не добавлять Flyway, Hibernate ddl-auto, schema.sql/data.sql или создание таблиц из Java-кода. Обычные INSERT событий и технические UPDATE версии потока во время работы выполняются через JDBC; они не являются миграциями.

Для новых миграций XML используется как индекс подключений, изменения — Liquibase formatted SQL. Базовый путь: `src/main/resources/liquibase`. Главный `master.xml` включает `changelog/YYYY.MM/YYYY.MM-changelog.xml`, месячный файл включает SQL-файлы `YYYY.MM.DD_ES-N_description.sql`. ES-N — уникальный локальный номер; Jira, чужие префиксы задач и чужой author не требуются.

Каждый SQL-файл начинается с `--liquibase formatted sql`, содержит уникальный `--changeset author:id`, осмысленный русский `--comment`, SQL и явную стратегию rollback. Не использовать чужой логин автора; выбрать устойчивый идентификатор проекта или реального автора.

Основной путь для нового проекта:

```yaml
spring:
  liquibase:
    change-log: classpath:liquibase/master.xml
  sql:
    init:
      mode: never
```

## Существующие миграции и данные

Уже применённые changesets не переписывать и не переименовывать. Идентичность changeset включает путь файла; перенос ради новой структуры может вызвать повторное применение. Сначала изучить текущие changelog и их использование.

Если проект уже использует YAML master или другой путь, сохранить исторические файлы и их идентичность. Для новых миграций использовать formatted SQL. XML master можно ввести с корректным подключением прежнего дерева, только если идентичность старых changesets сохранена; при сомнении оставить действующий master. Исторический YAML — допустимое исключение, а не повод переинициализировать БД. Liquibase остаётся единственным механизмом во всех случаях.

Один changeset — одно логическое изменение. Не создавать фиктивные DDL-изменения ради рефакторинга Java-пакетов. Rollback, удаляющий таблицу истории, является разрушительным: не выполнять автоматически. Если изменение без потери данных необратимо, документировать это и стратегию следующей корректирующей миграции, а не выдавать no-op за полноценный откат.

## Модель хранения Event Sourcing

| Таблица | Роль | Допустимые операции приложения |
|---|---|---|
| wallet_events | Неизменяемые бизнес-факты | INSERT, SELECT |
| event_streams | UUID и техническая current_version | INSERT, SELECT, атомарный UPDATE версии |
| command_receipts | Результат успешной команды для идемпотентности | INSERT, SELECT |

Баланс и статус кошелька не сохраняются как отдельный источник истины. Receipt может содержать исходный ответ с балансом, но GET и обработка новых команд не восстанавливают Wallet из receipt.

Событие содержит event_id, stream_id, stream_version, event_type, schema_version, payload JSONB, occurred_at TIMESTAMPTZ и command_id. Обязателен UNIQUE(stream_id, stream_version); event_id — PK. command_receipts.command_id — PK. Порядок replay определяется stream_version, а не временем или UUID.

## JDBC и SQL

Использовать JdbcClient/JdbcTemplate и параметризованные запросы. Явный SQL — штатная часть проекта; JPA-правила о nativeQuery, JPQL, Criteria и Specification здесь неприменимы. Spring Data/JPA автоматически не подключать. DTO projection в JPA и событийная проекция — разные понятия; ни одна не требуется первой версии.

Контракт CommandReceiptRepository: `Optional<CommandReceipt> find(UUID commandId)` и `void insert(CommandReceipt receipt)`. INSERT при дубликате должен обнаружить конфликт; не использовать upsert, перезаписывающий первоначальный fingerprint/ответ.

## Атомарная запись

Граница транзакции находится в реализации прикладного сервиса. События команды, изменение current_version и receipt фиксируются одним commit на одном DataSource/transaction manager.

Для существующего потока проверка ожидаемой версии выполняется атомарно:

```sql
UPDATE event_streams
SET current_version = current_version + 1
WHERE stream_id = :streamId AND current_version = :expectedVersion;
```

Пример предполагает одно событие команды, как в первой версии. Если событий несколько, прирост равен их числу и весь набор вставляется атомарно. Ноль обновлённых строк — конфликт. Проверка версии в Java или блокировка synchronized не заменяют SQL.

При создании запись event_streams и первое событие фиксируются одной транзакцией; конкурентное создание защищено PK. Новые события имеют версии без пропусков. При чтении полного потока версия восстановленного Wallet определяется событиями, прочитанными одним упорядоченным SELECT.

READ COMMITTED достаточно при описанном CAS-контроле записи. TransactionTemplate разрешён; @Transactional допустим при корректном proxy-вызове. Не добавлять независимые транзакции записи в репозитории.

## Идемпотентность и ошибка транзакции

Fingerprint учитывает тип команды, walletId и нормализованные поля, включая expectedVersion. При совпадении ключа и содержания вернуть сохранённый результат; при различии — 409. Успешный повтор не создаёт новых событий.

После релевантного конфликта полностью откатить транзакцию, затем отдельным чтением проверить receipt конкурирующей команды. Продолжать SELECT в уже аварийной PostgreSQL-транзакции нельзя. Сохранить обработку гонки, когда дубль успел завершиться между первоначальным поиском receipt и проверкой текущего состояния.

Не повторять списание автоматически с другой expectedVersion. Не превращать любую SQL-ошибку в VERSION_CONFLICT.

## Типы и индексы

Деньги — BIGINT/long в копейках, без double/float, с защитой от переполнения. Моменты событий — Instant/TIMESTAMPTZ. Настройки времени Hibernate и клиники не переносить. JSONB отображать явным сериализатором, типы событий выбирать из разрешённого реестра; не десериализовать произвольные Java-классы по данным БД.

Индексы вводить под конкретные запросы. UNIQUE(stream_id, stream_version) уже обеспечивает индекс для чтения истории кошелька. Не создавать дублирующий индекс без причины. Профилирование и EXPLAIN ANALYZE не являются обязательной задачей текущего рефакторинга; автоматические проверки поведения пользователь отложил.
