# Правила разработки Event Sourcing Wallet

## Цель и границы

Учебный Java-проект с прозрачной реализацией Event Sourcing. Полные требования находятся в `docs/PROJECT.md`. Перед изменениями прочитай этот файл и существующий код. Реализуй только этап, указанный в текущем запросе: инициализацию или рабочий сервис.

Стек: Java 25 без preview features, Spring Boot 4.x, Gradle Wrapper и Groovy DSL, PostgreSQL, Spring JDBC, Liquibase. Выбери совместимые стабильные patch-версии и зафиксируй их; не используй динамические версии, SNAPSHOT или milestone. Не заменяй заданные основные версии и инструменты ради обхода проблемы окружения.

## Ограничение пользователя: никаких тестов

Не создавай и не запускай unit-, integration-, end-to-end-, нагрузочные и иные тесты. Не добавляй JUnit, Mockito, Testcontainers, test starters, JaCoCo, `src/test`, тестовые fixtures и тестовые скрипты. Не запускай API-сценарии под видом smoke-тестов.

Разрешены чтение кода, разрешение зависимостей, компиляция, сборка `./gradlew bootJar` и обычный запуск приложения с миграциями. Примеры curl и SQL нужны только как документация для самостоятельного изучения; автоматически их не выполняй. Не запускай `test`, `check` или полный `build`. В отчёте отдельно укажи, что тесты по запросу пользователя отсутствуют.

## Архитектура

- Один Gradle-модуль, одно приложение, одна PostgreSQL. Базовый пакет `com.example.wallet`.
- `domain`: чистая Java, агрегат Wallet, команды, события, бизнес-ошибки. Никаких Spring/JDBC/Jackson/JPA-аннотаций.
- `application`: сценарии, транзакционные границы, интерфейсы хранилища и репозитория результатов команд.
- `infrastructure`: JDBC, SQL, сериализация событий, Liquibase и конфигурация.
- `api`: REST, DTO, валидация входа и обработка ошибок. Контроллеры не содержат бизнес-правил и SQL.
- Не строй универсальный Event Sourcing framework, command bus или сложную иерархию generic-репозиториев. Интерфейсы вводи на реальных границах домена и инфраструктуры.
- Используй constructor injection, records для неизменяемых значений и sealed interface для конечного набора событий. Не добавляй Lombok, MapStruct и JPA.

## Обязательные инварианты Event Sourcing

1. Источник истины о состоянии кошелька — неизменяемая последовательность событий. Таблицы с текущим балансом нет.
2. Состояние Wallet меняется только применением событий. Решение о новой операции и восстановление прошлого разделены: `decide(command)` возвращает новые события; `apply(event)` применяет факт; `rehydrate(events)` восстанавливает объект.
3. Replay детерминирован: не читает часы, случайность, сеть или БД; не запускает команды, не пишет события и не создаёт внешних эффектов. Новые бизнес-правила не применяются повторно к историческим командам.
4. События читаются в порядке `stream_version`, а не времени. Версии начинаются с 1 и идут без пропусков внутри кошелька.
5. Все события одной команды, изменение версии потока и результат для идемпотентности фиксируются одной транзакцией PostgreSQL. Ответ об успехе возвращается после commit.
6. Optimistic locking выполняется атомарно в БД через expected version. Проверка в Java или `synchronized` не заменяет её.
7. Идемпотентность хранится в БД, переживает перезапуск и учитывает совпадение ключа и содержания команды. Не продолжай использовать PostgreSQL-транзакцию после SQL-ошибки: сначала rollback, затем отдельное чтение результата конкурента.
8. Тип события в БД — стабильное имя из явного реестра, не полное имя Java-класса. Версия формата события и версия потока — разные поля. Неизвестное событие нельзя молча пропустить.
9. Изменения схемы выполняются только Liquibase. Применённые changesets не переписывай; добавляй следующие. Приложение не выполняет UPDATE/DELETE для сохранённых событий.

## Документирование кода

Документация, JavaDoc, содержательные комментарии и итоговые объяснения — на русском. Идентификаторы Java, API и SQL — на английском.

- Каждый значимый класс/интерфейс сопровождай JavaDoc: ответственность, место в потоке обработки, ограничения.
- Для доменных методов поясняй входные условия, результат, бизнес-ошибки и наличие/отсутствие побочных эффектов.
- Для `decide`, `apply`, `rehydrate`, `load`, `append` поясни различия между новыми событиями и replay.
- У транзакций и SQL объясняй границу атомарности, expectedVersion, поведение при гонке и причину выбранных ограничений.
- У сериализатора объясняй соответствие типов, payload и schemaVersion, реакцию на неизвестные версии.
- В Liquibase используй comments/remarks для назначения таблиц, столбцов и ограничений.
- Комментарии объясняют причину решения, а не пересказывают каждую строку. Не документируй тривиальные getters ради объёма.
- Поддерживай README и `docs/PROJECT.md` в соответствии с реализацией; не отмечай будущую возможность как готовую.

## Объём первой версии

Реализуй создание кошелька, пополнение, списание, закрытие, чтение текущего/исторического состояния и истории событий; optimistic concurrency и идемпотентность обязательны.

Не добавляй Axon, CQRS-инфраструктуру, проекции, eventual consistency, очереди, Kafka, outbox, Saga, Temporal, snapshots, кэш, микросервисы, UI, авторизацию, переводы между кошельками и upcasters. Поле schemaVersion заложи сейчас, миграцию старых форматов оставь будущему этапу.

## Работа и отчёт

Сохраняй существующие файлы пользователя. Не пересоздавай проект поверх рабочего кода. Не добавляй зависимости и новые сервисы без задачи, которую они решают в текущем объёме.

Делай текущую задачу до завершения без запроса подтверждения на обычные изменения. Если окружение не позволяет скачать зависимости или запустить Java/Docker, честно опиши ограничение; не подменяй PostgreSQL на H2, не понижай Java, не имитируй успешную сборку. Итог: что реализовано, как запустить, что фактически проверено и что осталось недоступным.
