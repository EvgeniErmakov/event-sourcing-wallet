# AGENTS.md — Event Sourcing Wallet

## Цель и приоритеты

Проект демонстрирует собственную реализацию Event Sourcing на Java 25, Spring Boot 4, Gradle, PostgreSQL, Spring JDBC и Liquibase. Код должен быть понятным и подробно документированным.

Следовать текущим указаниям пользователя. Этот AGENTS.md и адаптированные документы docs определяют текущие правила проекта. Старые промпты и примеры другого проекта не являются основанием возвращать JPA, менять расположение слоёв или добавлять тесты. При переносе новых правил обновить противоречащие описания в README и существующей спецификации, сохранив бизнес-контракты.

Перед работой прочитать `docs/PROJECT.md`, `docs/architecture.md`, `docs/database.md` и документы, относящиеся к изменяемому коду. Полный набор правил: architecture.md, code-style.md, checkstyle-rules.md, database.md, api-guidelines.md, code-quality.md, logging.md, security.md. Файл `docs/REFACTORING_PROMPT.md` описывает отдельную задачу; его присутствие не означает, что рефакторинг надо запускать при любом запросе.

## Стек

Java 25 без preview, Spring Boot 4.x, Gradle Wrapper с Groovy DSL, PostgreSQL, Spring JDBC, Liquibase. Сохранить совместимые точные версии существующего проекта; для нового — выбрать стабильные версии и зафиксировать. Gradle для запуска на JDK 25 — совместимая версия 9.x не ниже 9.1.0. Не понижать Java или Boot ради обхода ограничений среды.

Не добавлять Axon, JPA/Hibernate, Spring Data, Lombok или MapStruct в текущую задачу. Не строить универсальный Event Sourcing framework.

## Обязательные директории

Все REST-контроллеры — `controller`. Все собственные исключения — `exception` с подпакетами domain/application/infrastructure при необходимости. Глобальный RestControllerAdvice — `exception.api`.

Прикладные сервисы обязательно разделяются:

- интерфейсы — `service`, например WalletService;
- реализации — `service.impl`, например WalletServiceImpl implements WalletService;
- @Service ставится на реализацию, методы интерфейса реализуются с @Override;
- контроллер получает интерфейс через конструктор.

Это правило совместимо с Event Sourcing. Оно не переносит бизнес-правила из Wallet в сервис. Не создавать пары интерфейс/Impl для records, событий, Wallet, конфигураций и каждого helper.

Остальная структура: domain, domain.command, domain.event, dto.request, dto.response, service.model, repository, repository.jdbc, serialization, config; mapper только при необходимости. Сохранить существующий базовый пакет; новый проект использует com.example.wallet. Не оставлять дубли старых и новых компонентов после переноса.

## Разделение ответственности

Controller: HTTP, DTO, валидация формы, вызов интерфейса сервиса и HTTP-ответ.

WalletServiceImpl: прикладной сценарий, идемпотентность, загрузка потока, восстановление, вызов Wallet, транзакция и формирование результата.

Wallet: бизнес-инварианты и состояние. decide(command) формирует события, apply(event) применяет факт, rehydrate(events) восстанавливает историю. Состояние изменяется только через применение событий.

Repository/JdbcEventStore: SQL и технические гарантии записи. Domain не зависит от Spring, JDBC, Jackson, HTTP и DTO; exception.domain также остаётся чистой Java.

## Неизменяемые требования Event Sourcing

1. Источник истины — wallet_events. Таблица текущего баланса не создаётся.
2. Replay детерминирован: не вызывает команды, не сохраняет события, не генерирует UUID/время и не создаёт внешних эффектов. Новые правила приёма команд не проверяются заново на истории.
3. Порядок — stream_version, начиная с 1, без пропусков. Время события не определяет порядок replay.
4. События одной команды, изменение current_version и command_receipt фиксируются одной транзакцией. Успешный ответ возвращается после commit.
5. Конкурентная запись защищена атомарным expectedVersion в БД; проверки в Java или synchronized недостаточно.
6. Receipt только вставляется и читается. Контракт — find и insert, без перезаписывающего upsert. Дубль с тем же fingerprint возвращает исходный ответ; другой fingerprint — конфликт.
7. После ошибки PostgreSQL сначала rollback, затем отдельное чтение receipt конкурента. Не делать автоматический повтор списания с другой версией.
8. Event_type — стабильное имя из реестра, schema_version — версия payload. Рефакторинг Java-пакетов не меняет сохранённые типы и JSON. Неизвестную историю нельзя молча пропускать.
9. Деньги — long/BIGINT в копейках; суммы положительные, переполнение запрещено.
10. GET восстанавливает состояние из событий основной БД. HTTP-пагинация истории не обрезает полный replay.

## Строго Liquibase

Любые изменения схемы — только Liquibase. Нет Flyway, Hibernate DDL, schema.sql/data.sql и DDL из Java. Новые миграции — formatted SQL; XML-файлы подключают миграции по правилам docs/database.md.

Уже применённые changesets и их идентичность сохранить. Исторический YAML допустимо оставить подключённым; не переписывать миграции ради нового формата и не сбрасывать БД. При переносе master обязательно учитывать пути/идентичность. Рефакторинг пакетов не требует фиктивной миграции.

TransactionTemplate разрешён и предпочтителен для явной обработки rollback. @Transactional допустим при правильной границе сервиса и proxy-вызове; интерфейс сервиса не предписывает способ управления транзакцией.

## Стиль и комментарии

UTF-8, четыре пробела, до 140 символов в строке, содержательные английские идентификаторы. HTTP DTO с суффиксом Dto, сервисы с Service/ServiceImpl, controller с Controller. EventStore, append, decide, apply, rehydrate — разрешённые предметные имена.

Constructor injection через явный конструктор и final-поля. Records для неизменяемых данных. Optional для отсутствующего одиночного результата, пустые коллекции вместо null. Не ломать границы транзакции ради лимита длины метода.

JavaDoc и поясняющие комментарии — на русском. Документировать значимые классы и методы: ответственность, входы/выходы, ошибки, инварианты и эффекты. Для replay, append, CAS, JSON-реестра, fingerprint и конфликта после rollback пояснения обязательны. Не заменять документацию очевидным пересказом строк.

## Без тестов по запросу пользователя

Не создавать и не запускать никакие тесты, тестовые зависимости, fixtures, src/test, smoke/API/нагрузочные скрипты. Существующие пользовательские тесты не удалять и не запускать. Не запускать test/check/build.

Разрешены чтение кода, разрешение зависимостей, компиляция и `./gradlew bootJar`, если эта задача не запускает тесты через нестандартные зависимости. Обычный локальный запуск приложения с миграциями разрешён. Примеры curl и SQL — только документация, автоматически не выполнять.

## Ограничение объёма

Не добавлять CQRS-инфраструктуру, проекции, eventual consistency, snapshots, upcasters, Kafka, outbox, Saga, Temporal, кэш, микросервисы, UI, авторизацию, переводы между кошельками и внешнюю систему трассировки. Не удалять уже существующую пользовательскую защиту или тесты только потому, что они не входят в новый объём.

Не менять HTTP-контракт, историю событий, fingerprint и семантику операций ради стиля. Не удалять пользовательские файлы/данные/volumes. Не логировать секреты и не сообщать о выполненной операции до commit.
